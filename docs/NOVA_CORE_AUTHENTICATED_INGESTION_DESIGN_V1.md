# NOVA Core — authenticated observation ingestion design (V1)

## Decision

Do not enable public or browser-originated database writes in the current V1 API.

The first ingestion release should be a server-to-server interface. Browser clients must call their own trusted application backend; they must never receive a shared ingestion secret or Cloudflare Access service-token secret.

## Proposed trust boundary

1. A module backend or approved integration service authenticates to NOVA Core using a Cloudflare Access service token.
2. Cloudflare Access protects the ingestion route/application. NOVA Core validates the Access identity at the API boundary and maps the authenticated service identity to an explicit server-side allowlist.
3. The allowlist grants only named capabilities, such as submitting observations for an approved module. Authentication alone does not grant access to every site, asset, source, or metric.
4. NOVA Core validates the payload, resolves site/asset/source ownership, applies metric and unit rules, and assigns verification state server-side.
5. NOVA Core writes the observation and its audit event atomically. Repeated requests with the same source and idempotency key return the original accepted result rather than creating another observation.

Cloudflare Access service-token credentials belong only in protected server-side secrets. They must not be placed in `NEXT_PUBLIC_*` variables, browser bundles, local-storage metadata, source control, or client-visible API responses.

## Required request contract

A future `POST /api/v1/observations` request should contain:

- `site_id`, `asset_id` (optional only for site-level metrics), and `source_id`
- `module`, `metric`, finite numeric `value`, and explicit `unit` (the current D1 schema stores scalar numeric values; structured payloads require a separately versioned schema)
- `observed_at` as an RFC 3339 timestamp with timezone
- `idempotency_key` generated by the sending service
- `provenance`: provider/source identity, acquisition method, and source record reference where available
- `quality_flags` as a bounded list of controlled values

The server must assign `ingested_at`, authenticated actor/service identity, verification state, and audit metadata. Client-supplied actor identity, verified status, or audit fields must be rejected or ignored; they are never authoritative.

## Validation and authorization foundations

The branch includes `apps/api/services/observation_contract.py`, a side-effect-free Pydantic contract that rejects unknown fields, unsupported modules, malformed metric/unit identifiers, non-numeric and non-finite values, timezone-naive timestamps, timestamps more than five minutes in the future, duplicate or unknown quality flags, and client attempts to set server-owned trust fields. It normalizes timestamps to UTC. This validates input shape only.

The branch includes `apps/api/services/service_authorization.py`, a pure deny-by-default policy. It accepts only a typed `VerifiedServicePrincipal` supplied by a future signature-verifying authentication adapter and an exact server-side service-to-module-to-source allowlist. Wildcard grants are rejected.

The branch also includes `apps/api/services/cloudflare_access_identity.py`, which maps already-verified Cloudflare Access JWT claims into that principal. It requires the expected issuer and audience, `type=app`, `service_token_status=true`, a non-empty `common_name` service-token ID, and valid `iat`/`exp` claims. **It does not verify JWT signatures.** The caller must first verify RS256 and the signing key against the Access JWKS; decoded/unverified claims must never reach this adapter. Cloudflare documents the `Cf-Access-Jwt-Assertion` header, JWKS endpoint, RS256 signing, issuer/audience checks, and service-token `common_name`/`service_token_status` claims:
- [Cloudflare — Validate JWTs](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/)
- [Cloudflare — Application token claims](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/application-token/)

Tests cover strict observation payloads, exact grants, unknown identities, incomplete principals, cross-module attempts, unlisted sources, malformed grant configuration, wrong issuer/audience, expired tokens, and non-service-token identities.

**None of these modules is wired to HTTP headers or a route. No request is currently authenticated.** They do not prove site/asset ownership, enforce HTTP payload byte limits, or write to D1.

## Authorization rules

- Authenticate before parsing or writing a request body beyond safe request-size enforcement.
- Map each Access service identity to allowed modules and source identities.
- Verify that the source belongs to the declared module and that the site and asset relationship is valid.
- Do not allow a module service to write for another module by changing a JSON field.
- Restrict metric names, units, value types, timestamp windows, JSON depth/size, and request size.
- Apply rate limits at the edge and enforce per-source quotas.
- Return generic authentication/authorization errors; do not leak secrets, database internals, or whether unrelated site identifiers exist.
- Keep read-only public data retrieval (such as NASA POWER) separate from authenticated write permissions.

## Idempotency and audit

The current schema's unique source/idempotency-key constraint is a useful foundation, but implementation must handle uniqueness conflicts safely and return a deterministic response. Observation insertion and its audit event must commit together using a transaction/batch whose atomicity is verified against the actual Cloudflare D1 Python Workers runtime. Do not assume transaction semantics from local SQLite tests alone.

Before implementation, add tests for:
- missing, malformed, expired, or unrecognized Access identity
- authenticated but unauthorized module/source
- site/asset/source ownership mismatch
- unknown metric or incompatible unit
- invalid/future/stale timestamps and oversized payloads
- duplicate idempotency keys, including concurrent retries
- atomic rollback if audit insertion fails
- server-assigned provenance and verification state
- absence of secrets in logs and response bodies

## Rollout gates

1. Confirm Cloudflare Access service-token support and route protection for the deployed Worker/API path.
2. Configure service identities and secrets only in server-side environments; never expose them to browsers.
3. Add an integration test against the real Workers runtime or a faithful D1/Workers test environment.
4. Provision D1 only after reviewing the account's current free quotas and billing settings. A free tier is not a guarantee of zero charges.
5. Apply migrations and verify `GET /api/v1/storage/status` reports `ready`.
6. Deploy the authenticated write route disabled by default; enable it only after security tests pass.
7. Start with one non-production source and a small, reversible observation batch. Keep all recommendations human-reviewed and do not connect actuator controls.

## Current implementation status

This document is a design and acceptance contract, not an implemented ingestion endpoint. The deployed NOVA Core Worker remains stateless for observations. D1 has not been provisioned or bound. No observation write route, Access policy, service token, or training pipeline is active.
