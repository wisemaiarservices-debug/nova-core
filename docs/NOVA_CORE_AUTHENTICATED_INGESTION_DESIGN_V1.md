# NOVA Core — authenticated observation ingestion design (V1)

## Decision

Do not enable public or browser-originated database writes in the current V1 API.

The first ingestion release should be a server-to-server interface. Browser clients must call their own trusted application backend; they must never receive a shared ingestion secret or Cloudflare Access service-token secret.

## Proposed trust boundary

1. A module backend or approved integration service authenticates to NOVA Core using a Cloudflare Access service token.
2. Cloudflare Access protects the ingestion route/application. NOVA Core validates the Access identity at the API boundary and maps the authenticated service identity to an explicit server-side allowlist.
3. The allowlist grants only named capabilities, such as submitting observations for an approved module. Authentication alone does not grant access to every site, asset, source, or metric.
4. NOVA Core validates the payload, resolves site/asset/source ownership, applies metric and unit rules, and assigns verification state server-side.
5. NOVA Core writes the observation and its audit event atomically. Repeated requests with the same source and idempotency key return the original accepted result rather than creating another observation.

Cloudflare Access service-token credentials belong only in protected server-side secrets. They must not be placed in `NEXT_PUBLIC_*` variables, browser bundles, local-storage metadata, source control, or client-visible API responses.

## Required request contract

A future `POST /api/v1/observations` request should contain:

- `site_id`, `asset_id` (optional only for site-level metrics), and `source_id`
- `module`, `metric`, finite numeric `value`, and explicit `unit` (the current D1 schema stores scalar numeric values; structured payloads require a separately versioned schema)
- `observed_at` as an RFC 3339 timestamp with timezone
- `idempotency_key` generated by the sending service
- `provenance`: provider/source identity, acquisition method, and source record reference where available
- `quality_flags` as a bounded list of controlled values

The server must assign `ingested_at`, authenticated actor/service identity, verification state, and audit metadata. Client-supplied actor identity, verified status, or audit fields must be rejected or ignored; they are never authoritative.

## Validation and authorization foundations

The branch includes `apps/api/services/observation_contract.py`, a side-effect-free Pydantic contract that rejects unknown fields, unsupported modules, malformed metric/unit identifiers, non-numeric and non-finite values, timezone-naive timestamps, timestamps more than five minutes in the future, duplicate or unknown quality flags, and client attempts to set server-owned trust fields. It normalizes timestamps to UTC. This validates input shape only.

The branch includes `apps/api/services/service_authorization.py`, a pure deny-by-default policy. It accepts only a typed `VerifiedServicePrincipal` supplied by a future signature-verifying authentication adapter and an exact server-side service-to-module-to-source allowlist. Wildcard grants are rejected.

The branch also includes `apps/api/services/cloudflare_access_identity.py`, which maps already-verified Cloudflare Access JWT claims into that principal. It requires the expected issuer and audience, `type=app`, an empty `sub` (the documented service-token marker), a non-empty `common_name` client ID, and valid `iat`/`exp` claims; if `service_token_status` is present, it must be `true`. It also checks `nbf` when supplied. **It does not verify JWT signatures.** The caller must first verify RS256 and the signing key against the Access JWKS; decoded/unverified claims must never reach this adapter. Cloudflare documents the `Cf-Access-Jwt-Assertion` header, JWKS endpoint, RS256 signing, issuer/audience checks, and service-token `common_name`/`service_token_status` claims:
- [Cloudflare — Validate JWTs](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/)
- [Cloudflare — Application token claims](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/application-token/)

The branch also includes `apps/api/services/observation_ownership.py`, a pure policy for already-resolved D1 records. It requires an active matching site, a source with the exact source ID and module that is either global or scoped to that site, and (when supplied) an active asset belonging to the same site. Disabled sources are denied. An unverified source may submit an observation, but this does not upgrade the observation's verification status. The module performs no database reads itself; the future route must resolve rows using parameterized D1 queries.

Tests cover strict observation payloads, exact grants, unknown identities, incomplete principals, cross-module attempts, unlisted sources, malformed grant configuration, wrong issuer/audience, expired tokens, non-service-token identities, inactive sites/assets, disabled sources, and cross-site ownership mismatches.

The isolated Worker now also has `apps/ingestion-worker/src/observation-ownership.mjs`, a read-only D1 ownership resolver. When a D1 binding is present, the route requires an active site, a source with the exact module that is either global or scoped to that site and not disabled, and (if supplied) an active asset belonging to the same site. A failed lookup returns one generic authorization response. An unverified source remains unverified; ownership does not promote trust. The resolver performs parameterized reads only. The route still stops before any insert and returns `persistence_not_enabled` after successful ownership checks. Unit tests use a mocked D1 binding; they are not a live D1 runtime test.\n\nThe Worker also validates the observation request with `apps/ingestion-worker/src/observation-contract.mjs` before it reaches the storage gate. This runtime contract rejects unknown fields, non-finite or non-number values, unsupported modules/methods/quality flags, malformed identifiers, timestamps without a timezone, impossible calendar dates, invalid timezone offsets, and timestamps more than five minutes in the future. It normalizes accepted timestamps to UTC. The validator is intentionally separate from database ownership checks; it does not prove that a site, asset, or source exists or belongs to the caller. The route still does not persist or accept observations.\n\nThe isolated Worker prototype now lives in `apps/ingestion-worker/`. Unlike the Python claims-only adapter above, its `src/access-auth.mjs` verifies the RS256 signature with Cloudflare Access JWKS using the Workers Web Crypto API, refreshes JWKS when a key ID is not found, and validates issuer, audience, service-token claims, and token times. It follows Cloudflare's documented service-token JWT shape: `type=app`, `common_name` (the service-token client ID), and an empty `sub`; the documentation lists `service_token_status` as an additional identity claim, but its service-token example does not include it. It then applies exact service/module/source grants. The HTTP handler reads the Access assertion from `Cf-Access-Jwt-Assertion`, authenticates before reading the request body, enforces a 32 KiB streaming body limit, and fails closed. Its observation route intentionally returns `storage_not_configured` (503) after successful authentication and authorization: it does not accept or persist observations. No site/source/asset D1 lookup or write is wired.

CI now runs the Node.js security tests alongside the Python API suite. These tests use a locally generated RSA keypair and a mocked JWKS response; they verify real RS256 signatures in the test runtime, invalid claims/signatures, exact grants, and fail-closed HTTP behavior. Additional hardening rejects issuer URLs containing paths, invalid token time ordering, malformed/empty service grants, whitespace-padded source grants, and normalizes JWKS network/JSON failures into controlled availability errors. The JWKS outage tests use isolated issuers so the in-memory key cache cannot mask the failure path. They are not a live Cloudflare Access integration test.

**The prototype code is present, but no Access application/policy, service token, secret, D1 binding, or deployment exists.** The deployed public API remains unchanged.

## Public API versus protected ingestion topology

The currently deployed `nova-core-api.neohaven.workers.dev` serves public read-only health and NASA POWER retrieval used by browser-facing module dashboards. Protecting that entire Worker with a service-token-only Access policy would also block those legitimate public reads.

Cloudflare documents Worker-level Access protection for a specific Worker, including its `workers.dev` hostname, routes, and previews. Therefore the safer V1 topology is to keep the existing public read-only API separate and create a dedicated ingestion Worker (for example, `nova-core-ingest-api`) whose Worker-level Access policy permits only the approved Service Auth identities. This also avoids relying on CORS as an authentication control. CORS is browser policy, not server-to-server authorization.

Do not create or deploy that second Worker until the Access application, Service Auth policy, free-plan/billing implications, and required secrets are reviewed. No such Worker or Access policy currently exists. See [Cloudflare Workers Access protection](https://developers.cloudflare.com/workers/configuration/cloudflare-access/).

## Authorization rules

- Authenticate before parsing or writing a request body beyond safe request-size enforcement.
- Map each Access service identity to allowed modules and source identities.
- Verify that the source belongs to the declared module and that the site and asset relationship is valid.
- Do not allow a module service to write for another module by changing a JSON field.
- Restrict metric names, units, value types, timestamp windows, JSON depth/size, and request size.
- Apply rate limits at the edge and enforce per-source quotas.
- Return generic authentication/authorization errors; do not leak secrets, database internals, or whether unrelated site identifiers exist.
- Keep read-only public data retrieval (such as NASA POWER) separate from authenticated write permissions.

## Idempotency and audit

The current schema's unique source/idempotency-key constraint is a useful foundation, but implementation must handle uniqueness conflicts safely and return a deterministic response. Observation insertion and its audit event must commit together using a transaction/batch whose atomicity is verified against the actual Cloudflare D1 Python Workers runtime. Do not assume transaction semantics from local SQLite tests alone.

Before implementation, add tests for:
- missing, malformed, expired, or unrecognized Access identity
- authenticated but unauthorized module/source
- site/asset/source ownership mismatch
- unknown metric or incompatible unit
- invalid/future/stale timestamps and oversized payloads
- duplicate idempotency keys, including concurrent retries
- atomic rollback if audit insertion fails
- server-assigned provenance and verification state
- absence of secrets in logs and response bodies

## Rollout gates

1. Create a separate Cloudflare Worker project and protect its Worker hostname with a Cloudflare Access Service Auth policy; keep the public read-only API separate.
2. Configure service identities and secrets only in server-side environments; never expose them to browsers.
3. Add an integration test against the real Workers runtime or a faithful D1/Workers test environment.
4. Provision D1 only after reviewing the account's current free quotas and billing settings. A free tier is not a guarantee of zero charges.
5. Apply migrations and verify `GET /api/v1/storage/status` reports `ready`.
6. Deploy the isolated ingestion Worker with no D1 binding; verify Access blocks requests without a valid service token and that the authenticated route still returns storage-not-configured. Do not enable writes until the D1 integration and ownership tests pass.
7. Start with one non-production source and a small, reversible observation batch. Keep all recommendations human-reviewed and do not connect actuator controls.

## Current implementation status

This document is a design and acceptance contract plus an isolated, non-persistent Worker prototype. The deployed public NOVA Core Worker remains stateless for observations. D1 has not been provisioned or bound. The isolated Worker code is not deployed, no Access policy or service token is active, and no observation write is accepted. No training pipeline is active.
