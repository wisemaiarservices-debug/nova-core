# NOVA Core — Measurement Assessment Operation Recovery V1

Status: design proposal only. No runtime route, schema, migration, deployment, or production behavior is changed by this document.

## 1. Problem statement

The NOVA OS measurement-evidence page currently creates an Idempotency-Key in component memory and reuses it when a request is retried in the same mounted page. A full page reload discards that key. If Core committed an assessment but the response was lost, the reloaded browser cannot safely distinguish that case from an assessment that never reached Core.

Browser storage is not the authoritative fix. It can be cleared, copied across devices, exposed to same-origin script, or become inconsistent with server commits. A durable recovery contract must be owned by NOVA Core.

## 2. Goals and non-goals

Goals:
- Recover an assessment operation after reload, browser restart, or device change.
- Never create a second assessment merely because a response was lost.
- Preserve the existing separation between one-time transport nonce (x-nova-request-id) and stable operation idempotency.
- Re-authorize every operation read and mutation using the current Access identity, active tenant membership, and exact observation/site grants.
- Keep assessment rows immutable and preserve existing exact evidence/governance gates.

Non-goals:
- Treat an operation ID as authentication or authorization.
- Change the meaning of passed, failed, or not_assessed.
- Make an operation record proof of scientific validity.
- Store browser credentials, Access cookies, signed permits, or secrets.
- Automatically repeat an operation whose state is ambiguous.

## 3. Proposed resource model

Core owns a measurement_assessment_operations resource with guarded state transitions. Minimum fields:

| Field | Purpose |
|---|---|
| operation_id | Server-generated, high-entropy opaque identifier (at least 128 bits; 256 bits preferred) |
| tenant_id, site_id, observation_id | Exact immutable scope |
| actor_subject | Verified Access subject that initiated the operation |
| request_digest | SHA-256 digest of canonical operation inputs; never store raw secrets |
| state | reserved, running, completed, not_assessed, or terminal failed |
| assessment_id | Nullable FK/reference to the immutable assessment result |
| created_at, updated_at, completed_at | Server timestamps |
| lease_expires_at, attempt_count | Bounded worker recovery and operational visibility |

The operation row must be tenant/site/observation scoped with composite foreign keys where available. Actor and scope are immutable. State changes are guarded by conditional writes and append-only audit events. Do not persist caller-supplied identity claims.

## 4. HTTP contract (proposed)

All routes are private behind the existing Access gateway and Core's authenticated internal envelope. Exact paths and response schemas must be finalized during implementation.

1. **Resolve current operation** — retrieve the actor's latest unresolved operation for an exact tenant and observation; if none is unresolved, return the latest completed result when one exists. The query is scoped by the authenticated actor and current grants. It must not reveal another actor's operation.
2. **Reserve/reuse operation** — atomically return the actor's existing unresolved operation for the observation, or create one if none exists. Repeating the call after a lost response returns the same operation. The operation ID is generated by Core.
3. **Execute operation** — submit the operation ID and canonical request digest. Replays of the same operation and digest return the same durable state/result. A changed digest or observation is a conflict. Assessment creation and operation completion must be committed atomically where the storage engine permits, or reconciled through a uniquely constrained durable state machine.
4. **Read operation** — return only the minimal state and, when completed, the original assessment record. Re-authorize active tenant membership, observation read grant, and exact tenant/site scope on every read.

A client must never mint a replacement operation ID after a timeout. It resolves/reuses the server operation first. The transport request ID remains fresh and single-use on every gateway attempt.

### Explicit re-assessment

Historical assessments remain immutable. Starting a new assessment after a completed operation must be an explicit user action, not an automatic retry. Use compare-and-swap against the latest operation ID (the caller states which completed operation they are intentionally superseding). The server must atomically create at most one successor for that predecessor, so retrying a lost "start new assessment" response resolves to the same successor. This avoids a duplicate operation after reload without requiring local storage.

## 5. State machine and concurrency rules

- reserved -> running -> completed or not_assessed; terminal failed is permitted only for classified, non-retryable failures.
- A transient worker failure leaves a recoverable nonterminal state; a bounded lease permits another worker to resume. Lease takeover uses conditional update on the prior lease/version, never blind overwrite.
- Exactly one active operation per actor + tenant + observation. Enforce with a database uniqueness strategy, not only application checks.
- Exactly one successor per completed predecessor for explicit re-assessment.
- Assessment row, operation state, and audit event must not diverge. Use a transaction/batch with conditional constraints; if D1 cannot guarantee the required atomicity for the chosen path, design a recoverable outbox/reconciliation protocol before implementation.
- Same operation + same digest returns the original state/result. Same operation + changed digest, tenant, site, observation, or actor fails closed with conflict/denial.
- A stale or revoked source, mapping, calibration, policy, tenant, site, asset, or membership still blocks a new assessment under the existing final-write governance checks. Recovery of an already completed operation returns its immutable historical result; it does not recompute it.

## 6. Authorization and privacy requirements

- Operation IDs are identifiers, not bearer capabilities.
- Resolve, read, reserve, execute, and successor creation all require the current verified Access identity, active tenant membership, and exact observation/site grant.
- Return a non-enumerating not-found/denied response for cross-tenant or unauthorized operation IDs.
- Actor-scoped resolution must not expose another user's in-progress operation or result, even where both users can read the observation.
- Recheck authorization at mutation time, including after any queue/lease wait.
- Do not put operation IDs, observation IDs, or tenant identifiers into analytics, third-party logs, or URLs where avoidable. If IDs appear in paths, redact them from access logs.
- Bound response size, request size, polling frequency, and operation retention. Retention must not delete or mutate immutable assessment/audit history.
- No client-side storage of Access credentials, private keys, signed permits, or authoritative operation state.

## 7. NOVA OS recovery behavior

After loading the exact tenant and observation:
1. Call the actor-scoped resolve endpoint.
2. If an unresolved operation exists, show its state and offer safe resume/poll.
3. If the latest operation is completed/not_assessed, display that original immutable result. Do not silently create another assessment.
4. Only an explicit "Run a new assessment" action invokes successor creation with the expected latest operation ID.
5. Poll with bounded backoff and abort when tenant/observation changes. Ignore stale responses.
6. A network timeout or reload always returns to resolve; never generate a new idempotency key as an automatic recovery action.

The page may retain ephemeral UI state for responsiveness, but correctness must not depend on React refs, localStorage, sessionStorage, IndexedDB, or browser lifetime.

## 8. Required tests before implementation is accepted

- Lost response after reservation: retry reserve returns the same operation ID.
- Lost response after assessment commit: reload + resolve returns the original assessment ID and result; no duplicate row.
- Two concurrent reserve calls for same actor/tenant/observation return one operation.
- Two concurrent execution attempts for same operation produce one immutable assessment.
- Same operation with changed digest/observation/tenant/actor is rejected.
- Two concurrent successor requests against one predecessor produce one successor.
- Actor A cannot resolve/read Actor B's operation.
- Tenant/site grant revocation before resolve, resume, execute, or successor creation denies access.
- Source/mapping/calibration/policy revocation during assessment still blocks the final assessment insert.
- Lease expiry/recovery does not create duplicate assessments or overwrite a newer lease.
- Cross-tenant ID probing does not reveal resource existence.
- Browser reload and second-device recovery work without local browser storage.
- Retention and audit tests prove assessment history remains immutable.

Concurrency tests must use real disposable D1 integration with overlapping requests/transactions, not only mocked meta.changes=0 outcomes.

## 9. Delivery sequence

1. Review this contract against Core's current D1 schema, gateway envelope, authorization helpers, and assessment service.
2. Implement migration + service state machine + private Worker routes behind existing Access authorization.
3. Add gateway forwarding and strict CORS handling for any new browser-facing methods.
4. Add D1 integration tests for reservation, execution, successor, lease, and revocation races.
5. Update NOVA OS client/page to resolve and resume server-owned operations.
6. Run exact-head CI, independent security review, and staging Access/D1 E2E before any release decision.
