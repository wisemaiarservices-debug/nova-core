# Ingestion Worker authenticated local D1 integration test

This harness runs only in GitHub CI against the disposable local D1 database
created and seeded by the `apps/tenant-api` D1 integration steps.

## What it verifies

- The production ingestion request handler verifies a synthetic RS256 Access
  service JWT against a synthetic JWKS document before processing the request.
- Issuer, audience, service identity and exact module/source grant are checked
  through the same authentication and authorization functions used by the
  deployed Worker.
- Site, source and asset ownership are resolved from actual local D1 rows.
- A valid synthetic observation is persisted with the server-derived tenant ID.
- The observation remains `unverified`; ingestion does not confer scientific
  or operational verification.
- An exact retry returns the same observation ID and leaves one audit event.
- Reusing the idempotency key with a changed payload returns a conflict and
  preserves the original row.
- A source outside the exact service grant is denied before persistence.
- Cross-tenant site and asset references are denied without persistence.
- A test-only SQLite trigger rejects the audit insert; the D1 batch must roll
  back the observation insert as well and the Worker must not report acceptance.

## Deliberate boundary

`wrangler.local-d1-test.toml` selects a CI-only entrypoint and a local D1
binding. The entrypoint delegates `POST /api/v1/observations` to the same
`createIngestionHandler` used by the production Worker. Only two test
dependencies are injected: a JWKS resolver that returns the ephemeral public
key generated by the Node harness, and a deterministic request-ID factory for
the audit-failure trigger. The private key is generated in memory for each run
and is never written to the repository or sent to the Worker.

The `/__ci/ingestion/state` route is read-only and exists only in this local
test entrypoint to inspect the disposable D1 rows. The local-only configuration
sets `CI_TEST_INGESTION=true`; the deployed Worker entrypoint does not expose
this route or the injected JWKS resolver.

This is an end-to-end local integration of the production handler's RS256
verification, exact service grant, tenant ownership and persistence logic.
It is not a live Cloudflare Access/JWKS deployment test, a production D1 test,
or proof that the private tenant gateway is deployed.

Never run this configuration with `--remote`, never deploy this entrypoint,
and never point it at a non-CI database. The UUID in the local Wrangler config is
a placeholder used only by Wrangler's local D1 emulator.
